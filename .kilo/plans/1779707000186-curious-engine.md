# Robust EPG Format v2 Design & Implementation Plan

**Plan ID**: 1779707000186-curious-engine  
**Date**: 2026-05-25  
**Status**: Ready for implementation  
**Goal**: Replace the messy scraped `public/EPGs/1.json` structure with a robust, self-documenting, contributor-friendly JSON format (v2) that radio stations can reliably fill and return.

**Hard requirements from latest feedback**:
- Use **IDs** (`show_id` + top-level `shows` catalog) so stations never repeat program metadata.
- **No blocks at all** in v2 — only real `start` + `end` wall-clock times ("HH:MM"). Durations are always derived from the actual times.

The format must be easy to validate, minimize human errors, support explicit full schedules, and evolve the parser with minimal breakage.

---

## 1. Analysis of Current `public/EPGs/1.json`

The file (894 lines, Contrabanda FM, station id=1) is the **only** EPG in the project. It was scraped from their visual weekly grid (https://www.contrabanda.org/programacio/).

### Core Structure (v1, ad-hoc)
```json
{
  "station": "Contrabanda FM",
  "schedule_type": "weekly",
  "timezone": "Europe/Madrid",
  "block_unit_minutes": 30,
  "gaps": "Musica",           // string title for auto-filled interstitials
  "days": [ { "day": "monday", "label": "lunes", "programs": [ ... ] }, ... ]
}
```
Each program:
```json
{
  "start": "00:00",
  "title": "Nikosia",
  "category": "contrabanda" | "musica" | "podcast" | "directe",
  "duration_blocks": 4,
  "live": false,
  "url": "https://...",
  "frequency": "biweekly"     // only on 3 entries
}
```

### Critical Problems (Discovered via Static Analysis)
- **Incomplete coverage (biggest error source)**:
  - Only Mon/Tue: exactly 48 blocks (24h) with 0 interstitial gaps.
  - Wed: 45/48 blocks effective (3h unlisted after 22:30).
  - Thu: 46/48 (2h unlisted).
  - Fri: only 40/48 effective (starts 02:00, ends 22:00 — 4h morning + 4h evening unlisted).
  - Sat: 48/48 (good).
  - Sun: 47/48 (1h unlisted).
  - `getCurrentShow()` returns `null` (no show) for times outside `[firstListedStart, lastListedEnd]`, even when `gaps` is defined.
  - `getDaySchedule()` only inserts interstitial gaps; never adds filler before first or after last listed program.
- **Old duration via `duration_blocks` + implicit block grid is error-prone for humans** (and eliminated in v2):
  - Required mental math (4 blocks = 2h at 30 min unit). Easy to mistype when stations edit.
  - No explicit `end` time — the root cause of coverage bugs and off-by-one errors.
- **Recurrence data is dead weight**:
  - `"frequency": "biweekly"` (and `*` in titles) on Skarlata Ojara etc. — completely ignored by `getCurrentShow()` / `getDaySchedule()`.
  - All shows appear every week.
- **No metadata / presentation data**:
  - `metadata.categories` (expected by EPGModal + old plans) is absent → raw category keys shown.
  - Top-level `gaps` is a magic string + hardcoded category `'musica'` in logic.
- **Parsing fragility** (repeated in 3 places in logic.js):
  - Manual `"HH:MM".split(':')` with no validation, no midnight-crossing support, assumes exact 2-digit padded format.
  - `days` array + `find()` by english key (order-dependent for prev/next nav in modal).
- **Scraped inconsistencies**:
  - Some days list dozens of "Música" filler slots explicitly; others omit them (relying on runtime gaps).
  - Mixed categories ("directe" vs others).
  - No provenance (`last_updated`, `source`, `contact`).
  - Titles contain special chars/accents (JSON ok, but no normalization).
- **No validation / self-description**:
  - No JSON Schema.
  - No version.
  - Impossible for non-technical radio volunteers to contribute without introducing overlaps, wrong durations, repeated data, or missing hours.
- **Other**:
  - `schedule_type` present but unused (code assumes weekly 7-day grid).
  - No support for normalized show data (duplication if same show appears 5×/week).
  - No `description`, `hosts`, `notes` per program.
  - Assumes all programs fit in one day (no `end < start` cross-midnight).

**Conclusion**: Current format works for the one scraped case by accident but is **not** a safe template. It will produce bad data and broken UIs when other stations attempt to use it.

## 2. Design Goals for v2 (Incorporating Your Feedback)

- **Primary format**: Strict JSON + JSON Schema (your preference). Easy to validate with online tools or a provided script. No new runtime dependencies.
- **Explicit & complete by default** (your preference): Stations should list **every** time slot for their broadcast hours (including all filler "Música", "Off Air", automated music, etc.). This makes data self-contained, trivial to validate ("no overlaps, sequential, full coverage or documented partial"), and removes hidden magic. Runtime gap-filler logic kept only as a safety net for minor omissions.
- **IDs for programs / normalized catalog strongly preferred** (your explicit repeated request): Top-level `"shows"` catalog is the recommended way for stations to define each unique program once (title, category, url, description, hosts, recurrence_note, etc.). Daily grids then reference them with lightweight `{start, end, show_id, live?}` entries. This eliminates massive data repetition. Flat inline programs are still allowed (for simplicity or one-offs) but the template and docs will push the ID/catalog approach as best practice.
- **Recurrence**: Keep as human-readable note only for now (your preference). No week-parity math in current-show logic yet. Use `"recurrence_note"` or `"notes"` field; display it in modal if present.
- **Human-friendly for non-devs**:
  - Explicit `"start"` + `"end"` (HH:MM) — no block math required.
  - Clear contributor instructions (English primary + Spanish notes).
  - Full explicit grid examples.
  - JSON Schema + validation guidance (VS Code, online validator).
- **Robust for code**:
  - Versioned (`"version": "2.0"`).
  - Pure wall-clock time: every program has explicit `start` + `end` ("HH:MM"). Duration is derived as `(endMin - startMin)` minutes — **no blocks, no block_unit_minutes anywhere in v2**.
  - Support both old (compat) and new fields during transition (old files keep using blocks internally).
  - Optional but recommended `metadata` with categories map, default filler, etc.
  - Easy to extend (description, hosts, exceptions for holidays later).
- **Minimal code impact**: Parser enhancements are localized; UI (modal, dashboard alternation) needs almost no changes.
- **Deliverable for stations**: A ready-to-copy `template.json` + `EPG-FORMAT.md` (contributor guide) that you can email or link.

## 3. Proposed v2.0 Schema (Canonical)

```json
{
  "version": "2.0",
  "station": "Contrabanda FM",
  "station_id": 1,
  "schedule_type": "weekly",
  "timezone": "Europe/Madrid",
  "last_updated": "2026-05-25",
  "source": "https://www.contrabanda.org/programacio/",
  "contact": "contrabanda@contrabanda.org",
  "notes": "Some shows marked *Quincenal (biweekly) — check website for current week.",

  "metadata": {
    "categories": {
      "musica": "Música / Automated",
      "podcast": "Podcast / Reemisión",
      "contrabanda": "Contrabanda Original",
      "directe": "Directo / Live",
      "especial": "Especial / Monográfico"
    },
    "default_filler": {
      "title": "Música",
      "category": "musica"
    }
  },

  // OPTIONAL but recommended for DRY (your hybrid preference)
  "shows": {
    "nikosia": {
      "title": "Nikosia",
      "category": "contrabanda",
      "url": "https://www.contrabanda.org/programa/nikosia/",
      "description": "Long-running live show with guests and music.",
      "hosts": "Various"
    },
    "skarlata-ojara": {
      "title": "Skarlata Ojara",
      "category": "contrabanda",
      "url": "...",
      "recurrence_note": "* Quincenal (cada dos semanas)"
    }
    // ... all recurring shows defined once
  },

  "days": [
    {
      "day": "monday",
      "label": "Lunes",
      "programs": [
        {
          "start": "00:00",
          "end": "02:00",
          // flat style (simple for new contributors) — one-off or rare shows
          "title": "Nikosia",
          "category": "contrabanda",
          "live": false,
          "url": "..."
        },
        {
          "start": "02:00",
          "end": "02:30",
          "title": "Música",
          "category": "musica",
          "live": false
        },
        // ... every slot until sign-off (use actual wall times, no blocks)
        {
          "start": "13:00",
          "end": "15:00",
          // normalized style using show_id (strongly preferred to avoid repeating data)
          "show_id": "nikosia",
          "live": true
        }
      ]
    }
    // ... all 7 days, each with explicit full coverage of on-air hours using start+end only
  ]
}
```

**Rules for v2 programs** (enforced by schema + validator):
- **Strongly prefer `show_id`** referencing the top-level `shows` catalog (your explicit request). This eliminates repetition of title/category/url/description etc. Use inline `title`+`category` only for true one-offs or first-time simple templates.
- Either `show_id` **or** inline (`title` + `category`) — not both.
- `start` and `end` are **required** (HH:MM, 24h, zero-padded). No `duration_blocks`, no `block_unit_minutes` anywhere in v2 data.
- `end > start` (no cross-midnight programs in v2; split at 00:00 if needed).
- No overlaps within a day (validated by comparing start/end minutes).
- Stations are encouraged to list **every** slot explicitly for their broadcast hours (including filler music/off-air). The schedule is the source of truth.
- For limited-hour stations: explicitly list "Fuera de emisión" / "Closed" / "Música automatizada" slots, or document the broadcast window in day `notes`.
- Optional per-program: `description`, `hosts`, `recurrence_note`, `live`, `url`, `notes`.

**Backward compat**:
- Old v1 files (no `version` or `version < 2`) continue to work via fallback paths (they still use `duration_blocks` + `block_unit_minutes` internally during normalization).
- v2 files are pure `start`/`end` time; the normalizer computes `startMin`/`endMin`/`durationMin` directly from the clock times.
- New parser always normalizes to internal `{startMin, endMin, durationMin, ...}` shape (no blocks exposed to UI after v2).

### 4.2 Modify Existing Files

   - Add `version`, `station_id`, `last_updated`, `source`, `contact`, `notes`.
   - Add `metadata` with categories (map from site legend + current usage) + `default_filler`. **Remove all block_unit references**.

   - Result: clean, non-repetitive, pure time-based v2 file that is easy for other stations to emulate.

2. **`logic.js`** (core parser updates — localized)
   - Add `normalizeEpg(epg)` helper (idempotent).
     - v2 path (has `end` or `version >= "2"`): for each program compute `startMin`/`endMin` directly from `start`/`end` strings. Derive `durationMin = endMin - startMin`. No block math.
     - v1 legacy path: keep the old `duration_blocks * blockUnit` calculation (only for files without `end`).
     - Support `show_id` → lookup + merge fields from `epg.shows` (title, category, url, description, etc.). This is now the recommended way.
     - Normalize `metadata` (fall back to old top-level `gaps`/`block_unit_minutes` only for v1 files).
     - Always attach `startMin`/`endMin`/`durationMin` to every normalized program object.
   - Update `getCurrentShow(epg)` and `getDaySchedule(...)`:
     - Use the normalized `endMin` (never duration_blocks * unit for v2).
     - In gap insertion (getDaySchedule): compute inserted gap duration from actual minute delta, not blocks.
     - Return `durationMin` (and drop `blockUnit` from the daySchedule object for v2 data).
     - Keep existing `gaps` fallback for old v1 files only.
     - For v2, prefer `metadata.default_filler`.
     - Optional: on load, call a `validateEpg(epg)` that `console.warn`s for partial coverage, unknown categories, overlaps, etc. (dev aid, non-fatal).
   - Export `validateEpg` if useful for the script.
   - No behavior change for stations without EPG or old v1 files.

## 6. Validation & Quality Guarantees (New)

- JSON Schema covers structure, required fields, time format, enum categories (extensible).
- Custom validator (script) additionally checks:
  - No overlaps per day (start/end minute comparison).
  - Reasonable coverage (warn if large unlisted periods without explanation in `notes`).
  - All referenced `show_id` exist in the `shows` catalog.
  - `start < end` for every program.
  - Prefer use of `show_id` over repeated inline data (soft recommendation/warning).
- Contributor workflow: "Edit template.json → paste into https://www.jsonschemavalidator.net/ with our schema → run local validate script → send us the file."

## 7. Tradeoffs & Why This Design (Your Choices Incorporated)

- **JSON + Schema** (vs YAML/CSV): Matches your preference. Lowest friction for machine consumption, no parser dep, excellent validation story. CSV converter can be added later as a bonus script if demand appears.
- **Explicit full grids preferred**: Directly addresses the coverage bugs in the scraped file. Data becomes auditable by eye ("does 00:00-24:00 have 48 contiguous entries?"). Runtime filler is now a convenience, not a correctness crutch.
- **Hybrid shows**: Gives power users DRY + rich metadata without forcing complexity on simple contributors (they can stay 100% flat).
- **No machine recurrence yet**: Per your answer — avoids complex week-math and reference dates for v2. The note field + website link is sufficient and honest.
- **Pure start + end wall-clock times (zero blocks)**: Your explicit requirement. No `duration_blocks`, no `block_unit_minutes` in any v2 file or in the v2 code path. Duration for display/UI is derived purely as minutes between `end` and `start`. This is the simplest possible mental model for radio volunteers.
- Old block math is kept **only** inside the v1 compatibility shim for the existing 1.json during the transition. After migration of 1.json, the block concept can be deleted from the codebase entirely.
